## 1. 목표

Won Design Studio를 단순 제작사가 아니라 기업의 중요한 웹사이트와 디지털 제품을 함께 수행하는 **Digital Experience Partner**로 인식시키고, 검증된 프로젝트와 안정적인 업무 방식을 근거로 프로젝트 상담 전환을 만듭니다.

초기 공개에서 방문자가 다음을 판단할 수 있어야 합니다.

- WDS가 사업을 이해하고 시작한다.
- 디자인과 개발을 하나의 결과로 연결할 수 있다.
- 프로젝트 과정과 품질 관리 방식이 체계적이다.
- 출시 이후 안정화와 개선까지 맡길 수 있다.
- 현재 프로젝트를 상담해 볼 가치가 있다.

## 2. 초기 공개 범위

### 포함

| 경로 | 역할 | 핵심 콘텐츠 |
| --- | --- | --- |
| `/` | 브랜드와 수행 역량의 전체 서사 | 기획서에 정의된 Home 11개 섹션 |
| `/work` | 수행 경험 탐색 | 문제 정의와 역할 중심 프로젝트 목록 |
| `/work/[slug]` | 프로젝트 증명 | Marketing Catnip, TimeAttack, Questboard 상세 |
| `/services` | 제공 범위와 제외 범위 설명 | Diagnostics, Corporate Website, Digital Product, Operation & Improvement |
| `/approach` | 과정과 품질 관리 신뢰 형성 | Discovery부터 Stabilization과 Improvement까지 |
| `/about` | 존재 이유와 조직 방향 설명 | Purpose, Mission, Vision, Values, Team & Partners |
| `/contact` | 상담 리드 접수 | 필수 입력, 예산, 첨부, 동의, 성공·실패 상태 |
| `/privacy` | 개인정보 처리 고지 | 실제 운영 정책에 맞는 승인 문안 |
| `not-found` | 잘못된 경로 복구 | Home, Work, Contact 이동 |

기술 리소스에는 페이지별 metadata, Open Graph, canonical 정책, `sitemap.xml`, `robots.txt`가 포함됩니다.

### 초기 제외

- Insights 독립 목록과 상세
- Products 독립 페이지
- Careers 독립 페이지
- CMS 편집 화면
- 다국어 페이지

About 안에서는 Products & Experiments와 Careers를 향후 방향 수준으로만 다룰 수 있습니다. 별도 페이지와 링크는 콘텐츠 준비 후 추가합니다.

### 임시 권장안

Website Diagnostics CTA는 초기에는 `/services#website-diagnostics`로 연결합니다. 별도 상품의 대상, 산출물, 기간과 상담 흐름이 확정되면 독립 상세 페이지를 별도 결정으로 추가합니다.

## 3. 실행 원칙

### 콘텐츠 진실성 우선

- 실제 프로젝트 원고와 공개 가능한 화면을 레이아웃보다 먼저 준비합니다.
- 가짜 고객사, 추정 성과, 확인되지 않은 수치와 임시 후기는 사용하지 않습니다.
- 협력사 또는 간접 수행 프로젝트는 고객사, 계약 주체와 WDS의 실제 역할을 구분합니다.
- 공개 승인 근거가 없는 항목은 빌드 단계에서 제외하거나 차단합니다.

### 디자인 승인 후 구현

- 전체 Home의 리듬과 각 주요 섹션을 읽을 수 있는 크기의 조정된 콘셉트를 먼저 만듭니다.
- Work 목록·상세, Contact, Header/Footer와 모바일 상태까지 구현 전에 설계합니다.
- 한 장의 압축된 긴 화면만으로 세부 디자인을 추측하지 않습니다.
- 승인된 콘셉트의 카피, 계층, 색상, 이미지 처리, 컨테이너와 컴포넌트 구성을 구현 기준으로 잠급니다.
- 콘셉트 생성 과정에서 AI 이미지를 사용할 수 있지만, 실제 고객 프로젝트를 대신하는 공개용 가짜 이미지는 사용하지 않습니다.

### 정적 우선, 운영 기능은 서버 검증

- 공개 콘텐츠는 초기에는 코드 기반으로 관리합니다.
- 페이지는 Server Component와 정적 생성을 우선합니다.
- 모바일 메뉴, Contact와 필요한 모션만 Client Component로 구현합니다.
- Contact는 클라이언트 검증만 신뢰하지 않고 서버에서 동일한 규칙을 다시 검증합니다.

### 실제 브라우저 검증

- 시각 구현은 섹션 또는 연속된 뷰포트 단위로 승인 콘셉트와 비교합니다.
- 데스크톱, 태블릿과 모바일에서 레이아웃과 핵심 흐름을 확인합니다.
- 키보드 탐색, focus, reduced motion과 오류 상태를 수동으로 확인합니다.
- 구현 완료 전 승인 콘셉트와 최신 브라우저 캡처를 직접 비교하고 차이 기록을 남깁니다.

## 4. 기술 기준안

아래 항목은 Phase 0 의사결정에서 최종 승인하기 전까지 기준안입니다.

- Next.js App Router
- TypeScript strict mode
- Tailwind CSS와 CSS Custom Properties 기반 디자인 토큰
- SUIT 로컬 호스팅. 사용 전 배포 라이선스 확인
- React Hook Form과 공유 Zod 스키마
- 프로젝트 메타데이터는 Zod로 검증하고 본문은 MDX로 관리
- Contact Route Handler에서 서버 검증, 영구 저장, 담당자 알림 처리
- 첨부파일은 이메일에 직접 포함하지 않고 비공개 스토리지 참조로 전달
- honeypot, 서버 rate limit, 필요 시 추가 스팸 방지 도입
- Preview와 Production 배포 환경 분리
- lint, typecheck, test와 production build를 병합·배포 게이트로 사용

공급자 의존 기능은 문의 저장, 파일 저장, 알림과 분석 어댑터 뒤에 격리해 교체 가능하게 만듭니다.

## 5. 마일스톤

### M0. 범위·콘텐츠·운영 정책 확정 — 현재 단계

주요 결과물:

- 페이지와 URL 범위
- 콘텐츠·에셋 인벤토리
- 공개 승인 및 사실 검증표
- Contact, 개인정보, 분석, 도메인 결정
- 페이지별 완료 기준

종료 게이트:

- 초기 Work 3건의 필수 원고와 주요 이미지가 준비되어 있습니다.
- 고객명, 로고, 화면과 역할의 공개 가능 여부가 기록되어 있습니다.
- Contact 저장, 알림, 첨부, 보관과 개인정보 처리 방식이 결정되어 있습니다.
- 도메인, 리디렉션과 초기 언어 범위가 결정되어 있습니다.
- 열린 P0 결정이 없거나 승인된 유예 사유가 있습니다.

### M1. 시각 콘셉트와 디자인 시스템 승인

주요 결과물:

- 전체 페이지 리듬을 보여주는 Home 개요
- Home 주요 섹션별 읽을 수 있는 독립 콘셉트
- Work 목록과 상세 템플릿
- Services, Approach와 About의 페이지 구성
- Contact 기본, 오류, 제출 중과 성공 상태
- Header, Footer, 모바일 내비게이션
- 모바일 핵심 화면과 반응형 재배치 기준
- 색상, 타이포그래피, 간격, 컨테이너, 미디어, 아이콘과 모션 토큰
- 첫 화면 허용 카피 목록과 전체 보이는 문구 잠금

종료 게이트:

- 각 콘셉트의 원본 경로와 승인 상태가 기록되어 있습니다.
- 실제 프로젝트 이미지의 비율과 처리 방식이 확정되어 있습니다.
- Home 11개 섹션의 중복 여부와 전체 리듬이 승인되어 있습니다.
- 구현자가 추측해야 하는 주요 화면이나 상태가 남아 있지 않습니다.

### M2. Foundation

주요 결과물:

- 프로젝트와 패키지 버전 고정
- 라우팅과 기본 레이아웃
- 디자인 토큰과 SUIT 적용
- Header, Footer, Skip link와 focus 기준
- 콘텐츠 스키마와 로더
- 기본 metadata, sitemap, robots와 404
- 테스트, CI와 Preview 배포

종료 게이트:

- lint, typecheck, test와 production build가 통과합니다.
- 모든 초기 경로가 Preview에서 접근 가능합니다.
- 콘텐츠 스키마가 누락 필드와 승인되지 않은 공개 항목을 감지합니다.

### M3. Home 구현

Hero와 Featured Work를 첫 번째 수직 슬라이스로 구현하고 승인 콘셉트와 비교한 후 나머지 섹션을 순서대로 연결합니다.

종료 게이트:

- Home 11개 섹션이 승인된 목적과 순서를 충족합니다.
- Marketing Catnip이 가장 강한 프로젝트 증거로 보입니다.
- 데스크톱, 태블릿과 모바일에서 핵심 메시지와 CTA 우선순위가 유지됩니다.
- 보이는 카피, 색상, 타이포그래피, 이미지 처리와 레이아웃 차이가 해결되어 있습니다.

### M4. Work와 Core Pages

주요 결과물:

- Work 목록과 3개 상세
- Services, Approach와 About
- Next Project와 Contact CTA 연결
- 실제 콘텐츠, 이미지와 alt text

종료 게이트:

- 모든 메뉴, 카드와 CTA가 실제 목적지로 연결됩니다.
- Work 상세가 문제, WDS 역할, 접근 방식과 확인 가능한 결과를 전달합니다.
- placeholder, 가짜 정보와 공개 미승인 에셋이 없습니다.

### M5. Contact, SEO와 운영 연결

주요 결과물:

- Contact 전체 입력과 예산 필수 선택
- 서버 검증, 중복 방지, 저장, 첨부와 담당자 알림
- 제출 중, 성공, 실패와 재시도 상태
- 개인정보 동의와 처리방침
- 페이지별 metadata, OG, canonical, sitemap과 robots
- 승인된 전환 이벤트와 오류 관측

종료 게이트:

- Production과 동등한 환경에서 정상, 검증 실패, 서버 실패, 중복과 첨부 제한을 확인합니다.
- 제출 기록, 동의 시각, 알림과 재시도 근거를 확인할 수 있습니다.
- Preview는 검색 노출이 차단되고 Production 설정은 올바릅니다.

### M6. 출시 QA

주요 결과물:

- 기능, 링크, 콘텐츠, 접근성, 반응형, 브라우저, 성능과 SEO 검수
- 콘셉트 대 브라우저 fidelity ledger
- 배포 및 롤백 런북
- 최종 공개 승인

종료 게이트:

- `docs/qa/acceptance-criteria.md`의 필수 항목이 통과합니다.
- 실제 Production 문의를 1회 제출해 저장, 알림과 성공 화면을 확인합니다.
- 공개 도메인, canonical, robots와 sitemap을 재확인합니다.

### M7. 안정화

- 출시 후 폼 성공률, 오류, 핵심 전환과 페이지 상태를 점검합니다.
- 발견 사항을 우선순위가 있는 개선 백로그로 전환합니다.
- Insights, Products, Careers와 CMS 도입 여부를 실제 운영 요구에 따라 다시 결정합니다.

## 7. 변경 관리

- 범위나 정책 변경은 `docs/decisions/open-decisions.md`에 새 결정 ID로 기록합니다.
- 콘텐츠 또는 에셋 변경은 인벤토리와 공개 승인표를 함께 갱신합니다.
- 승인된 콘셉트 이후 보이는 카피나 레이아웃을 바꾸면 변경 이유와 재승인 상태를 기록합니다.
- 현재 단계와 다음 게이트는 `docs/planning/current.md`만을 기준으로 확인합니다.
